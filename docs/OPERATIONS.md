# Operating with stack-kit

Generated by `stack-kit help --markdown` from the verb registry (lib/cli/verbs/); regenerate, never edit.
Every verb runs the same in a terminal and in CI. A verb that changes a server prints its plan -- the
exact remote paths and commands -- before it acts; `--plan` stops there and writes nothing.

## Exit codes

| code | meaning |
|---|---|
| 0 | done (or, with --plan, planned) |
| 1 | failed: a step or a declaration was wrong; the message names it |
| 2 | not run: a usage error, or nothing selectable (no target, a pending one, a non-workspace environment) |
| 3 | refused: ownership -- the directory carries another project's marker, or none |
| 4 | refused by the preflight: runtime, ports or disk |
| 5 | refused: provenance -- a dirty checkout or an archive without release.json where a clean commit is required, or a release that cannot run as its service is declared now |
| 6 | unhealthy: a service did not become healthy (a release in a rolling-back environment was rolled back) |
| 130 | interrupted |

## Deploy and operate

### `backup`

a store's dump in the layout's backups place, and a restore that is checked, not assumed.

```
stack-kit backup <store> --env <id> [--plan]
stack-kit backup verify <store> [--file <name>] --env <id> [--plan]
stack-kit backup replay --env <id> [--plan]
stack-kit backup list <store> --env <id>
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--file <name>` | verify: the dump to check (default the newest) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

How a store dumps, restores, is queried and dropped is its catalog entry (run inside its container, its credentials read there); what a restore must still hold is the host's (stack.infra.backup.<store>.anchors). verify restores into a uniquely named throwaway database (its files moved, never over the source), compares each anchor there and drops the database, pass or fail; replay applies the whole migration chain to an empty throwaway database (stack.migrate.replay) and drops it the same way. Both print their plan first.

Exit codes: 0, 1, 2, 6.

```
stack-kit backup postgres --env prod
stack-kit backup verify postgres --env prod
```

### `deploy`

build -> package -> ship -> up -> health, for a module or all, to one environment.

```
stack-kit deploy <module|all> --env <id> [--target <t>] [--plan] [--yes] [--artifact <archive>]
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--artifact <archive>` | deploy this archive (CI: the one packaged earlier) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

An environment that requires a clean checkout refuses a dirty one; one that asks first (`confirm`) asks on a terminal and refuses without one unless --yes. A commit already packaged is not rebuilt. A failed health rolls back where the environment declares it.

Exit codes: 0, 1, 2, 3, 4, 5, 6.

```
stack-kit deploy api --env dev --plan
stack-kit deploy all --env prod --yes
```

### `infra`

the infra stack: on this machine, or on the target in its layout's infra place.

```
stack-kit infra local up|down|status [--prod]
stack-kit infra remote sync|up|down|status|purge --env <id> [--target <t>] [--plan] [--yes]
stack-kit infra tunnel --env <id> [--target <t>]
```

| option | |
|---|---|
| `--plan` | print the plan and stop; nothing is written |
| `--yes` | answer the confirmation (CI) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

Exit codes: 0, 1, 2, 3, 4.

```
stack-kit infra remote up --env dev --plan
stack-kit infra tunnel --env dev
```

### `layout`

move this project's services out of a tree laid out before the layout.

```
stack-kit layout migrate --target <t> --env <id> [--approve] [--yes]
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--approve` | apply the planned moves (never automatic) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

Only what the target declares as this project's (`legacyLayout`) moves, never a folder a listing finds; a direct child of the shared root is never moved.

Exit codes: 0, 1, 2, 3.

### `ops`

operate a deployed environment, per service, module or tier (or all).

```
stack-kit ops status|logs|start|stop|restart|rebuild [module|service|tier ...] --env <id>
stack-kit ops restart-check [module|service|tier ...] --env <id>   (restart is idempotent: healthy, same image, no drift)
stack-kit ops rm <module|service|tier ...> --env <id> [--yes]
stack-kit ops nuke --env <id> [--yes]
stack-kit ops prune [--schedule [--at '<cron>']] --env <id>   (builder cache and dangling images only)
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--follow` | logs: keep following |
| `--tail <n>` | logs: lines (default 200) |
| `--schedule` | prune: install it in the target user's crontab, once per host |
| `--at <cron>` | prune --schedule: the cron schedule (default weekly) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

rm and nuke ask first and act only inside the project's own environment directory, which must carry this project's ownership marker; never at the target's root.

Exit codes: 0, 1, 2, 3, 6.

```
stack-kit ops status --env prod
stack-kit ops logs api --env dev --follow
```

### `package`

build once: the driver's package step, then one archive of this commit with its provenance.

```
stack-kit package <module|all> [...]
```

| option | |
|---|---|
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

The archive is `.stack-kit/artifacts/<module>-<commit>[-dirty].tgz` with its sha256 beside it; `release.json` inside it carries the commit, `git describe --tags --always --dirty` and the services.

Exit codes: 0, 1, 2.

```
stack-kit package api
```

### `release`

a unit's releases, and moving `current` back.

```
stack-kit release list [module ...] --env <id>
stack-kit release rollback [module ...] [--to <id>] --env <id>
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--to <id>` | the release to roll back to (default: the one before current) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

`list` marks `current` with `*` and, with `!` and why, a release that cannot run as its service is declared now. `rollback` is a transaction: such a release is refused (exit 5) with nothing changed and the remedy (deploy that commit); otherwise the stack is brought up on the release -- its image built when missing -- and `current` moves only once each service is healthy on that release's image. Any failure brings the previous release back up, `current` never having left it, and exits 6 naming the failure and the build log.

Exit codes: 0, 1, 2, 3, 5, 6.

```
stack-kit release list --env prod
stack-kit release rollback api --env prod --yes
```

### `targets`

the declared deploy targets: list, plan the tree, create it, verify it, check health.

```
stack-kit targets [--plan] [--env <id>]
stack-kit targets --init --target <t> --env <id> [--plan]
stack-kit targets --verify --target <t> --env <id>
stack-kit targets --health --target <t> --env <id>
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--init` | create the project's tree with its ownership marker (idempotent) |
| `--verify` | read-only: marker, tree, current, prune limit, runtime, ports, disk |
| `--health` | the target's declared health URLs answer below 400, and its OIDC provider is ready (discovery, JWKS) |
| `--attempts <n>` | health: attempts per URL (default 12) |
| `--pause <s>` | health: seconds between attempts (default 5) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

--init refuses a non-empty directory without this project's marker; --verify reads the declared state (places, marker, compose file, env and runtime config digests, each service's running release, runtime, ports, disk) against the host, read-only, and exits 1 on drift, 2 when nothing could be verified; a drift is undone by the verb that owns it (deploy, release rollback).

Exit codes: 0, 1, 2, 3, 4.

```
stack-kit targets --plan
stack-kit targets --init --target linux --env dev
```

### `tls`

TLS on a private network: an internal CA on the target, a leaf per host, a public password-less truststore.

```
stack-kit tls ca --env <id>
stack-kit tls leaf <host> [--san <name,ip,...>] --env <id>
stack-kit tls truststore [--out <dir>] --env <id>
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--san <list>` | leaf: further DNS names and IPs |
| `--out <dir>` | truststore: where the public files go (default ops/deploy/tls) |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

The CA's key is made on the target and never leaves it; `ca` never replaces one. A leaf (397 days) lands where the edge template reads it (infra/tls/live). The truststore holds only the CA certificate, so it needs no password.

Exit codes: 0, 1, 2.

## Remote dev

### `dev`

remote dev: the module's source synced into its workspace and run by its driver's dev container.

```
stack-kit dev up <module|all> [--target <t>] [--plan]
stack-kit dev up <module|all> --mode hybrid|local|docker   (this machine)
stack-kit dev sync <module> [--full]
stack-kit dev watch <module|all>
stack-kit dev down <module|all>
stack-kit dev logs <module> [--follow]
stack-kit dev status
stack-kit dev shell <module>
stack-kit dev tunnel <module>
```

| option | |
|---|---|
| `--plan` | print the plan -- remote paths and commands -- and stop; nothing is written |
| `--yes` | answer the confirmation (CI); without a terminal a confirmation is otherwise refused |
| `--mode <mode>` | up: a local mode instead (hybrid, local, docker) |
| `--full` | sync: compare every file again (after a lost connection) |
| `--no-infra` | up --mode hybrid: the infra stack is running already |
| `--no-tunnel` | up --mode hybrid: open no tunnel |
| `--follow` | logs: keep following |
| `--target <name>` | the declared deploy target (default: the environment's) |
| `--env <id>` | the environment (catalogs.environments; --dev / --prod are short for it) |

The workspace is the layout's ({root}/{project}/dev/{tier}/{service}/workspace). A sync uses rsync when both ends have it, else the built-in index + tar stream over ssh; env files, keys and credential files are never sent. `watch` polls (no extra dependency), debounces, syncs, and reacts as the driver declares: hot-reload, restart, or rebuild; a lost connection is retried and followed by a full sync.

Exit codes: 0, 1, 2, 3, 4, 6.

```
stack-kit dev up api --target linux --plan
stack-kit dev watch api
stack-kit dev tunnel api
```

## The project

### `<step>`

a lifecycle step (catalogs.lifecycle: lint, build, test, ...) for every module, fail-fast.

```
stack-kit <step> [module ...]
```

Exit codes: 0, 1, 2.

```
stack-kit build
stack-kit test api
```

### `config`

the configuration catalogue's env-value policy against this machine's env files (names, never values).

```
stack-kit config check [module ...] [--env <id>]
```

The same policy every release runs before it writes an env file: required (or required only in an environment), no placeholder, a minimum length, a format (positive-int, url, https-url without localhost), values an environment forbids (a wildcard CORS origin in prod), keys another requires.

Exit codes: 0, 1.

```
stack-kit config check --env prod
```

### `extend`

extend the kit through a declared point: a host file or entry from its template, pending answers shown, template upgrades merged.

```
stack-kit extend --list
stack-kit extend <point> [<name>] [--plan]
stack-kit extend module [--approve <who>]   (draft the modules from the tree)
stack-kit extend env <folder> --env <id> [--plan]   (an ignored env file from the configuration catalogue)
stack-kit extend --upgrade [--plan]
stack-kit extend --init [--root <dir>] [--plan]
```

| option | |
|---|---|
| `--list` | every point: purpose, where the host file goes, status (unused | drafted | answered) |
| `--plan` | print what would be made or merged; nothing is written |
| `--upgrade` | merge each changed template 3-way into the host's file; a conflict is reported, never written |
| `--init` | every point init requires, then each infra service the manifest selects |
| `--root <dir>` | the host root (init, before a manifest exists) |
| `--approve <who>` | module: write the draft, recording who approved it |
| `--env <id>` | env: the environment whose ignored env file is made |

A point's file is made only on demand, never overwritten; the answers only the host can give are <<pending: ...>> markers that validate shows (an error where the manifest's `extend.profile` requires the point). A file where a point lives that no point declares is reported. The kit copy is never edited. `extend env` makes a folder's ignored .env.<env> from the configuration catalogue: non-secret values filled, a SECRET pending (config reports it, a deploy refuses it), a generated key a fresh value never printed.

Exit codes: 0, 1, 2.

```
stack-kit extend --list
stack-kit extend infra-service postgres --plan
stack-kit extend catalog-environments staging
```

### `init`

bootstrap a host, or draft its manifest from the tree.

```
stack-kit init
stack-kit init --plan
stack-kit init --approve <who>
```

`--plan` drafts the manifest from the evidence each driver declares (declared fields always win); `--approve <who>` writes the draft.

Exit codes: 0, 1, 2.

```
stack-kit init --plan
```

### `migrate`

carry a host's older declarations into their current homes.

```
stack-kit migrate [--apply]
```

Without --apply it lists what would change. It is the only reader of the legacy homes (deploy.env, .env.deploy, DEPLOY_*/COMPOSE_* keys): it moves their values into the manifest and the targets file, and removes them.

Exit codes: 0, 1.

### `migrations`

the migrations' ledger: a recorded one is never edited or removed; each is structure only.

```
stack-kit migrations check
stack-kit migrations lock
```

`lock` records every migration the drivers' declarations find (sha256, line endings normalised) in ops/stack-kit/migrations.lock.json; validate then refuses a recorded migration that changed or is gone.

Exit codes: 0, 1.

### `mod`

a command a module's driver declares, or a rung of its delivery ladder.

```
stack-kit mod <module> <command> [operands]
stack-kit mod <module> deliver <rung> [--env <id>] [--plan]
stack-kit <alias> <command> [operands]
```

A rung `via` a kit verb runs that verb (release -> deploy, remote-dev -> dev up, hybrid -> hybrid boot).

Exit codes: 0, 1, 2.

```
stack-kit mod api build
stack-kit mod api deliver release --env prod --plan
```

### `render`

write what a deploy runs into the host as generated projections: each module's container recipe, each environment's stack compose.

```
stack-kit render [--plan]
stack-kit render --check
```

| option | |
|---|---|
| `--plan` | say what would be written |
| `--check` | report a projection its sources no longer render |

Each file carries a header naming its sources -- edit those, not it. The release id and the packaged artifact's name are written symbolically ({release}, the driver's artifact glob). validate reports a stale projection; a release refuses one (exit 5). Paths: manifest `projections.containers` (default ops/containers/{module}/Dockerfile) and `projections.stack` (default ops/compose/stack/{environment}/compose.yml).

Exit codes: 0, 1.

### `scan`

the secret boundary: credential-shaped values in the tracked tree (and, --history, every commit).

```
stack-kit scan secrets [--history]
stack-kit scan secrets --fingerprint <file> <key>
```

| option | |
|---|---|
| `--history` | every line any commit added, too |
| `--fingerprint <file>` | print the sha256 of the value at <key> in this file, for its knownExposures row |

JWTs, passwords in URLs, connection-string passwords, private keys, committed env files, binaries in the tooling directories, and values the operator lists as leaked (security.knownLeaks: sha256 fingerprints). Placeholders are not values; a value the configuration catalogue tracks (knownExposures) is not failed twice -- matched by its row's `fingerprint` (sha256; `--fingerprint <file> <key>` prints it, never the value).

Exit codes: 0, 1, 2.

### `stack`

the local development stack, run by this machine's declared compose invocation.

```
stack-kit stack <up|down|ps|logs> ... [--env dev|prod]
```

Exit codes: 0, 1, 2.

### `validate`

validate the manifest, its declarations and the deploy targets.

```
stack-kit validate [--stages]
```

Exit codes: 0, 1.

## Drivers

From `drivers/registry.json`. `init --plan` drafts a module for each directory whose files a
driver's detection holds for; a host adds its own with `extend driver <name>`.

| driver | for | roles | recognised by | built by | writes |
|---|---|---|---|---|---|
| `dotnet-aspnet` | ASP.NET Core - dotnet run / dotnet publish artifact (Windows or cross-platform host) | api | `*.csproj` | - | `bin/`, `obj/` |
| `dotnet-library` | .NET class library - dotnet build / dotnet test of a library and its test project (no run, package or release) | other | - | - | `bin/`, `obj/` |
| `java-boot` | JVM — Spring Boot, built by Gradle or Maven (JAR deploy) | api, worker | `build.gradle`, `build.gradle.kts`, `settings.gradle`, `settings.gradle.kts`, `pom.xml`, `*/build.gradle`, `*/build.gradle.kts`, `*/pom.xml` | maven, gradle | `build/`, `.gradle/`, `target/` |
| `node-api` | Node — HTTP service (pnpm build + dockerized deploy, Fastify/Express/Nest) | api | `package.json` | - | `node_modules/`, `dist/` |
| `node-spa` | Node - single-page app run by its own package.json scripts (Angular CLI, Vite, React, Vue, Svelte) | ui | `package.json`, `angular.json` | - | `node_modules/`, `dist/`, `.angular/` |
| `node-vite` | Node — SPA dev remote + nginx release image (Vite, Angular, Nx) | ui | `package.json`, `vite.config.ts`, `vite.config.js`, `vite.config.mjs` | - | `node_modules/`, `dist/` |
